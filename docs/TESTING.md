# Testing conventions

These rules apply across the SDK, Nocterm TUI, Flutter app, and Windows integration boundaries. Feature ownership and safety contracts live in [architecture](ARCHITECTURE.md); commands and CI setup live in [development](DEVELOPMENT.md#workspace-development-and-ci). Follow [Flutter Redux test ownership](FLUTTER_ARCHITECTURE_CONVENTIONS.md#migration-test-ownership) when implementing that approved architecture.

## Responsibility and integration

- Give each behavior one primary test owner: that component, class, or layer tests its behavior thoroughly. A consumer tests only its own contract and must not repeat the owner's full behavior suite. Before keeping a consumer test that exercises a dependency, answer: “What specific Ludava bug would this catch that the owner's tests would not?” If there is no defensible answer, remove or narrow the test.
- Test application-owned behavior, not the implementation or documented behavior of frameworks and dependencies. Do not add tests merely to prove Flutter widget-building mechanics, Redux `StoreConnector(distinct: true)` rebuild suppression, Equatable's comparison algorithm, or GetIt's resolution mechanics. Required DI registration-presence assertions are the narrow exception described below. Test Ludava's nontrivial integration or configuration only when it protects a distinct application-owned contract; use the library's behavior as a premise, not a separate test target.
- Do not test mechanical delegation: an unchanged getter/setter, simple method forwarding, wrapper returning a collaborator's stream or value, or constructor forwarding does not justify tests by itself. A Ludava wrapper's existence is not a behavior to cover. Test its own transformations, filtering, argument selection, access restrictions, side-effect suppression, error translation, ownership, or lifecycle contracts when they are nontrivial. Do not create several tests proving that raw bytes passed into a stream emerge unchanged unless Ludava owns a distinct buffering/decoding/ordering behavior. If tests only restate a delegate's documented behavior, remove them without replacement.
- Isolate consumer tests at existing dependency-injection boundaries. Mocktail is the default for mocking collaborator objects and injected dependencies; use explicit stubs and interaction verification only for behavior owned by the subject under test, without generated mocks. Do not introduce production interfaces or factories solely for testing. Purpose-built fakes are exceptions only when they simulate meaningful stateful protocols, byte-addressable memory, native/FFI transfers, or controlled stream timing more clearly than mocks; justify and keep them focused. Flutter composition tests may render real child widgets to verify parent-owned composition and callback forwarding, but must not repeat a child's own behavior tests.
- Integration tests must establish a distinct integration contract, such as callback wiring, notification propagation, resource ownership, focus handoff, or lifecycle ordering. The same failure stimulus may appear at multiple layers only when each assertion protects a different owner responsibility; for example, rejecting a partial write, closing its native handle, invalidating session state, and showing a UI failure are separate contracts.
- Keep policy matrices at their policy owner. The SDK owns generic write eligibility, identity, bounds, and memory safety decisions; frontends test representative approved/denied presentation and their response to changing eligibility, not every SDK condition again.
- Test behavior at its owner: SDK tests own SDK behavior, TUI tests own terminal behavior, and Flutter tests own widget behavior. Parent widget tests own composition and wiring; they do not repeat a child's focused behavior tests. Integration tests cover important dependency boundaries and orchestration risks, not every unit-test condition again.
- Injection-container tests check only required registration presence, for example `expect(sl.isRegistered<TrainerSdkCapability>(), isTrue)`. Do not resolve registered instances to test their identity, values, factory output, operational behavior, or GetIt mechanics in DI tests. Put unique initialization, initial-state snapshot, shared-resource, and disposal contracts in the app/lifecycle/middleware/bridge tests that own those behaviors; never discard unique safety or lifetime coverage merely to simplify a DI test.

## Mock assertions and prohibited side effects

- An assertion must prove the full contract named by its test, not just one example invocation. For a **forbidden operation** (no memory read, no write, no refresh, no native close, no SDK call), `verifyNever` must match **all arguments** that could invoke that method, such as `verifyNever(() => repository.read(any(), any()))` or `verifyNever(() => capability.writeField(any(), any()))`. A negative check with one hardcoded address, field ID, or value is insufficient for a whole-operation prohibition. Exact negative arguments are appropriate only when the stated contract forbids *that particular argument*, not the operation itself. Apply this rule to every SDK, TUI, Flutter, native, and integration test.
- For a **required operation**, verify its exact relevant arguments and expected call count where those are part of Ludava's contract. For tests requiring **only the permitted effects**, verify both sides: the expected calls/output and the absence of additional or forbidden calls/output. After verifying every allowed interaction on a dedicated mock, use `verifyNoMoreInteractions(mock)` when **all** of that mock's interactions are in scope. For example, a terminal sanitizer must forward the sanitized string exactly once and emit **no extra writes**, including combined strings containing forbidden control bytes; `verifyNever` for individual control-only strings does not establish this. Where unrelated legitimate calls occur, instead assert absence of **all forbidden operations** with argument-wide matchers without policing irrelevant interactions.
- Do not blanket-verify every incidental collaborator call, assert `verifyNoMoreInteractions` against a shared mock with legitimate unrelated operations, or invent negative assertions for behavior outside the test's contract. Do not replace meaningful outcome assertions with mock-call assertions; preserve both observable results and side-effect boundaries when each matters.

## Data, fixtures, and isolation

- Generic behavior tests use synthetic `GameProfile` and `GameField` values. Frontend tests use synthetic profiles and session snapshots. They must not depend on current production game names, IDs, hashes, offsets, registration order, or a shared mutable catalog. The shared catalog-integrity suite and focused integration tests may use the production catalog for those specific responsibilities.
- Do not require a test file for each game or mirror ordinary game-profile tests across the SDK and frontends. One shared, data-driven catalog suite validates every registered profile against structural invariants without a hardcoded profile list or count. Keep exceptional game-specific tests only for unique behavior, regressions, or special mappings. Record game research and live-game evidence in `docs/games/`; passing automated tests does not establish game/build compatibility.
- Tests prove observable Ludava-owned behavior, a contract, invariant, failure mode, or regression. Do not test raw constant values, enum members/order/`.values`, static style presets, unchanged constructor assignments or defaults, ordinary per-game data, child behavior already covered by its owner, or private implementation details. Test nontrivial application-defined methods, derived properties, transformations, and validation implemented on an enum or value object; preserve safety-relevant invariants, semantic mappings performed by logic, layout, accessibility, and lifecycle behavior at their owners.
- Organize test files as imports, local mock classes/fixtures/top-level helpers, and finally `main()`. No top-level helper, mock, fake, or fixture declaration after `main()`. Within `main()`, put shared test variables and minimal `setUp`/`tearDown` before test groups; set up only what tests share, and isolate and release stateful resources reliably. Keep helpers local by default, using concise named overrides. Put shared helpers in package-local `test/support/` only for genuine reuse; do not introduce universal fixture frameworks, test service locators, or unnecessary dependency containers.
- Keep tests independently maintainable: ordinary profile-data changes must not require generic SDK, TUI, or Flutter behavior-test changes; tests must not leak mutable state or rely on execution order.

## SDK safety and native integration

- Preserve distinct safety and lifecycle cases. Do not combine different rejected preconditions merely to shorten a suite. Cover unverified profiles, unsupported/read-only fields, missing confirmation, stale or incorrect process identity and PPU hash, process termination/change, memory-base changes, invalid values/ranges, address overflow, incomplete transfers, native and preliminary-read failures, read-back mismatch, cleanup failure, rejected dependency calls, and correct disposal. Never weaken write protection to simplify tests.
- Use controlled native API mocks or a dedicated memory simulator for deterministic memory boundaries; unit tests must not read or write a live game's memory. Test Windows adapters through injected native calls and retain focused Windows integration tests for important native seams.
- Keep tests for root compatibility entry points and run those checks in workspace CI alongside the SDK and TUI suites.

## Naming and placement

Use one top-level group per *meaningful tested behavior*, public method, derived property, validating constructor, or component responsibility; a member's existence alone does not require a test. Name groups and scenarios by the behavior under test:

| Subject | Group | Scenario |
| --- | --- | --- |
| Method | `Method methodName() behaves correctly` | `Method methodName() <outcome>` |
| Property | `Property propertyName behaves correctly` | `Property propertyName <outcome>` |
| Constructor | `Class TypeName construction` | `Class TypeName initializes <observable result>` |
| UI component (Nocterm or Flutter) | `Class ComponentName <observable area> behavior` | `Class ComponentName <observable outcome>` |

- Use observable outcomes such as `returns`, `preserves`, `rejects`, and `throws`; add `when <condition>` when the condition is not already clear. Property names have no parentheses. Assert component output, interactions, and callbacks/actions through public interfaces.
- Do not use nested test groups. Test negative and boundary cases for safety checks, and pair a test expecting a collaborator call with a test showing it is not called when a precondition fails.
- Use Dart/Flutter's source-to-test mapping for focused tests: `<package>/lib/<relative-path>/file.dart` → `<package>/test/<relative-path>/file_test.dart`. Preserve IDE **Go to Test** navigation; do not require tests for every class or game profile.
- SDK tests must run without Nocterm or interactive stdin; TUI tests mock SDK collaborators by default and use a specialized stateful memory/terminal simulator only when its behavior is integral to the test. Workspace CI must analyze and test each package explicitly rather than assuming root commands discover every workspace package.

## Nocterm input tests

- Test raw terminal sequences at the input boundary when decoding affects visible behavior, including fragmented/coalesced input. Test component output and dispatched actions through public APIs. Cover cancellation-without-write, unavailable-values-not-zero, and invalid-input-not-written.

## Flutter widget and presentation tests

- **Widget behavior:** Test meaningful widgets at their responsibility. Cover startup and connection, SDK-provided values and permissions, explicit editing and cancellation, successful and failed writes, stale-session invalidation, process selection, semantics, and keyboard focus. Preserve dynamic fields, including profiles with multiple fields.
- **Test ownership:** SDK tests own write eligibility, validation, revalidation, and verified read-back. Theme tests own semantic mappings and central styles; widget tests own component-specific style overrides. Prefer behavioral assertions over pixel-perfect goldens unless a stable golden adds clear value.
- **Themes and layout:** Cover semantic colors in application widgets and standard Material controls, style-preset application through theme construction (not literal preset values), initial/minimum window sizes, compact widths, overflow, long titles and values, and scrolling. Test normal, editing, and error states at both 520 × 360 and 480 × 340 logical pixels; assert stable row geometry and no overflow.
- **Native window:** Inject only the native actions needed for widget-test seams. Verify actual dragging, resizing, minimize/maximize/restore, and DPI behavior in Windows integration tests.

- Flutter tests that need GetIt use isolated scopes. See [Flutter Redux test ownership](FLUTTER_ARCHITECTURE_CONVENTIONS.md#migration-test-ownership) for reducer, middleware, selector, ViewModel, bridge, DI, and native-close responsibility splits.
